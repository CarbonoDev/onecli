## What upstream shipped

One feature commit, [#470 `834af80`](https://github.com/onecli/onecli/commit/834af80) — "install page,
per-connection resources, approvals bell" — plus the release bump. It contains four things:

1. A project-scoped `/install` page replacing the Get Started modal, with a tool picker, live setup-status
   card, and per-agent pinning. Backed by new agent last-seen/activity plumbing.
2. An approvals bell that works on flat-edition pages, via a new `hasProjectContext()` helper.
3. A **resource boundary** layer: granular repo/folder scoping extended down to individual agent-connection
   grants and up to an org-level ceiling (`resource-axis.ts`, `org-resource-boundary.ts`).
4. Deferred credential minting in the gateway — don't mint a live upstream credential for a request that is
   about to be denied.

Most of it merges clean. Two things make this **not** a mechanical merge, both verified directly against the
merge tree rather than inferred:

### 🔴 Blocker — upstream's fail-closed check silently kills our granular resource scoping

`apps/gateway/src/connect.rs:1375` now reads:

```rust
if needs_scoped_token && !scoped_token_minted && !crate::ee_apps::has_request_guard(provider) {
    return None;
}
```

In this fork all three conditions are permanently satisfied for any scoped connection:

- `needs_scoped_token` is true for any non-empty `session_policy` (`connect.rs:1256`)
- `scoped_token_minted` can only become true via `ee_apps::try_refresh_credentials`, which is a stub
  returning `None` (`ee_apps.rs:12-18`), so `from_scoper` is always false
- `has_request_guard` is a hardcoded `false` (`ee_apps.rs:36-38`)

So **every resource-scoped GitHub/Dropbox connection our UI can create stops injecting any credential** —
`resolve_access_token` returns `None`, `build_connection_rules` returns `None`. This is a total, silent
regression of `5fa5509` (granular resource scoping). It lands as a _clean auto-merge_ and `cargo test` stays
green, because `scope.rs`'s tests are pure `evaluate_scope` unit tests that never reach `resolve_access_token`.

**Fix before building**: make `has_request_guard` return true for the providers we actually guard at the
request layer — `evaluate_scope` dispatches on exactly `("github-app"|"github", Repositories)` and
`("dropbox", Folders)`; everything else already falls to `Indeterminate → Blocked`, so the request layer is
fail-closed for the rest.

### 🔴 `keys.ts` merged clean and broken

`apps/web/src/lib/api/keys.ts` has **two `projects:` keys in the same object literal** — line 63 (ours:
`{all, detail}`) and line 73 (upstream's: `{all, list}`) — with zero conflict markers. TS1117 build failure;
if it compiled, the later wins and `queryKeys.projects.detail` becomes `undefined`, breaking `useProject` and
`project-name-card.tsx`. Collapse into one `{ all, detail, list }`.

## Open decisions for a human

1. **Two incompatible scoping models.** Upstream mints a per-request scoped credential and now fails closed;
   we enforce at the request layer in `policy_engine/scope.rs` and inject an ordinary broad token. Recommend:
   implement `has_request_guard` now (restores parity, one line), and treat "real token scoper in
   `ee_apps::try_refresh_credentials`" as its own later project — the deferred-minting plumbing that just
   landed is built for exactly that, and a leaked scoped token is itself bounded.
2. **Ungate runtime boundary composition, or ship write-time-only?** Recommend write-time-only this cycle
   with the comment corrected, and runtime composition as the next tracked ungating item.
3. **Implement `GET /v1/projects`?** Recommend yes, filtered through `canAccessProjectAsUser` / ProjectAccess
   bindings — returning every project in the org would leak project names past those bindings.
   `resolveOrganizationId` already validates membership on `X-Organization-Id`, so no middleware change.
4. **Existing rows with an empty scope list.** `scope.rs::parse` maps `ListShape::Empty → None` ("empty list
   = all", `scope.rs:91`), so a stored `{"repositories": []}` means _unrestricted_ today. Upstream's API fix
   only stops new ones. Recommend fixing `parse` to deny-all **and** auditing existing rows first —
   behaviour flips from unrestricted to blocked for those connections.
5. **`resource-scope.tsx` props.** `readOnly` is non-negotiable: `manage-permissions-dialog.tsx:272` merged
   with no conflict passing `readOnly={readOnly || save.isPending}`, so ignoring it renders org-granted grants
   as editable checkboxes. Do **not** copy upstream's `|| readOnly` early return — the dialog passes
   `save.isPending`, so the Resources block would blink out mid-save.
